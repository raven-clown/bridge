# bridge part 2: review, ship and release

Each task below is one GitHub issue. Work them in order; steps use checkboxes for tracking. Tasks 1 to 9 finish milestone v0.1 (review); tasks 10 to 17 are milestone v0.2 (ship and release).

**Goal:** Review a pull request's diff in the terminal with line and range comments kept as local drafts, submit the review, then merge with a per-repository policy, approve fork runs, rerun failed jobs, update the branch, sync the local clone, and cut a GitHub release with generated notes, all from the TUI and the CLI.

**Architecture:** Same layering as part 1. `forge` gains review, ship and release methods; `forge/github` implements them over REST and GraphQL; new library packages `review`, `ship` and `release` hold the logic and never touch the terminal; `internal/tui` gains `reviewview`, `shipview` and `releaseview`; `cmd/bridge` gains `review`, `ship`, `approve-runs`, `rerun`, `update-branch` and `release`.

**Tech Stack:** as part 1: Go 1.26 (toolchain 1.27.4), bubbletea, bubbles, lipgloss, glamour, go-git, cobra, yaml.v3.

**Spec:** [`docs/design.md`](../design.md). Part 1's plan and ledger rulings stand; the interfaces named here are the ones on main after part 1.

## Global Constraints

- Everything in part 1's Global Constraints still holds: one static binary, no `exec` of any program, Windows first class, no telemetry, the token never in files, logs, errors or fixtures, forge text only through `internal/termsafe`, tests first, no network in tests, no bare `time.Sleep`, no em-dashes, no mention of code generation tools, no co-author trailers.
- Every action that changes GitHub asks first when its `confirm.*` key is true: `confirm.review` before submitting a review, `confirm.merge` before merging, `confirm.release` before creating a release. Defaults are true.
- Merge defaults: method `squash`, title `{title} (#{number})`, body empty, `delete_branch: true`, `require_green: true`. Templates take `{title}`, `{number}`, `{author}`, `{branch}`, `{repo}`, `{version}`.
- Release defaults: tag `v{version}`, `bump: prompt`. Notes sections: Added from `feat`, Fixed from `fix`, Changed from everything else, each line `<title> by @<author> in #<number>`, then New Contributors, then `**Full Changelog**: <compare URL>`.
- Post-merge sync never discards local work: a dirty worktree, a branch other than the merged head or the default, or a default branch that cannot fast-forward means "skip and say why".
- Post-merge sync fetches over HTTPS with the token as basic auth (`x-access-token`), whatever the remote URL says, since go-git's SSH agent support does not work on Windows and its file transport runs `git`.
- Lock files collapse by default: `go.sum`, `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `Cargo.lock`, `poetry.lock`, `composer.lock`, `Gemfile.lock`, `uv.lock`. Generated files collapse: paths under `vendor/` or `dist/`, names ending `.min.js`, `.pb.go`, `_gen.go`, `.gen.go`, and any file whose first added line contains `Code generated` and `DO NOT EDIT`.

## Review Focus

1. GitHub omits `patch` for binary files, files over its size limit, and every file past the 3000th. Such a file must show "binary or too large to show" with its +/- counts, not an empty diff, and adding a comment on it must be refused with that reason. Test in Task 4 (parser) and Task 7 (view).
2. The head moves while a review is in progress (a push or force push). Submitting against the old head makes GitHub answer 422 because commented lines may no longer exist. The draft must record the head it was written against; submit must compare it to the current head first and ask, and a 422 must keep the draft. Test in Task 6.
3. Branch protection refuses a merge (405 "required status check" or "review required"). The message is shown verbatim, the branch is not deleted and the local clone is not touched. And when someone pushes to the branch between the merge and the delete, the branch is kept. Test in Task 11 and Task 12.
4. A pull request from a fork: its head branch lives in another repository, so the branch delete must be skipped (not attempted on the base repository) and post-merge sync runs only on a clone of the base repository. Test in Task 12.
5. A repository with no release yet. Notes take every merged pull request up to a cap of 100 with a line saying so, the Full Changelog link points at the commits list instead of a compare, and the first version is `0.1.0` unless the user gives one (`--version` or `set version`). And a tag that already exists on another commit stops the release, since GitHub would ignore the target and publish the old commit. Test in Task 15 and Task 16.
